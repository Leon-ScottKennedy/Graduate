# 按需求比例分析整机

“整机优化”现在提供游戏电竞、内容创作、日常办公、AI计算四条可拖动的需求条。初始主用途占70%，其他各10%。调整一项时，其余项目按原比例重新分配，最大余数法处理整数舍入，合计始终100%；其他项原本全部为0时均分剩余比例。

这些数字表示用途的重要性，不是硬件预算百分比，也不是性能评分。拖动不会请求AI或改变配置。用户点击“让豆包给出建议”后才发送请求。

`BuildDemandOptimizer.vue`通过`discoverRecommendations`提交当前配置、总预算、全部需求比例和基础兼容规则，使用`purpose=workload`。后台验证四项均为0—100的整数且合计100，再将完整比例交给豆包。工作负载模式允许返回不同配件类别的具体型号，解释用途取舍及可让出预算的类别，而非被当前点击的配件限制。旧的similar/rebalance接口仍保持原类别约束。

豆包建议随后匹配标准目录、数据库报价及已有补采流程。`BuildOptimization.vue`分别核算每个目标类别的独立整机方案，显示替换部件、预算来源、参考总价、预算余量和兼容检查。各方案不叠加，用户选择应用一套后，需要基于新配置重新分析。找不到型号、价格缺失、预算不足或存在明确兼容冲突时不能强行应用；AI不生成实际报价。

创作或AI占比达到25%时，整机降配和目标替换均不减少当前内存、SSD容量；AI达到25%时也不减少目标显卡显存。其余供电、预算、兼容及容量底线沿用原方案引擎。占比影响AI选型方向与这些底线，不表示程序能够保证相应性能。

修改需求比例、预算、主用途或当前配置会取消待返回请求并清除旧结果。缓存键包含需求比例；分析结果只在输入快照仍匹配时展示。初步建议已由豆包提供，页面不再自动为每套结果重复发送评审请求；用户仍可手动要求再次分析具体方案，并携带原始四项比例。

相关验证：`npm run test:demand-weights`、`npm run test:optimization`，后端`tests/test_recommendations.py`覆盖比例校验和跨类别AI建议。
